# KEY DASH × スタックチャン：デザイン検証

## 結論

**1のプレイ画面と3の結果画面を組み合わせる方向を推奨します。** 単語を読む時間には小さな相棒として置き、プレイが終わったら大きな表情を見せると、タイピングの読みやすさと愛着を両立しやすいと考えます。

これは画像モックの比較検討です。コード、動作アプリ、公開サイト、ランキングには変更していません。実機検証・利用者テスト・アニメーションの性能計測は行っていません。画像の数値は説明用サンプルです。

## 320×170画面での検討条件

- 実際の既存ゲーム画面と結果画面を参照画像として添付し、生成り #f3eedf・濃緑 #253b39・緑 #257b68 を継続。
- 公式リポジトリのStack-chan画像を添付し、黒いM5Stackの箱、シンプルな白い目と口、前面3ボタン、短い台座の特徴を参照。
- 32:17の横長画面として生成。これは拡大した概念画像で、320×170に実装されたスクリーンショットではない。
- 設計目安は、本文・操作案内12px以上、単語24〜28px、主要スコア36px。生成画像がこの寸法を厳密に満たすと断言はできない。
- 字数の長い既存単語「feather」を使い、キャラクターと競合しないかを目視比較。
- 入力欄、残り時間、WPM、正確率、Space/Backspace/Escの操作案内を残す。
- ミスは文字と「BACKSPACE TO FIX」で示す。キャラクターだけに正誤の意味を持たせない。

## 動きを付ける場合の仮説（未実装）

- キーを押すたびに動かすのではなく、単語の確定時に一度だけ小さく反応する。
- 打ち間違いを責める表情より、修正ができたときの小さな肯定を優先する。
- 結果画面は普通の完走でも笑顔。自己ベストのときに表情や小さな飾りを変える程度にする。
- 長い吹き出し・会話・新しい育成メーターは追加せず、今のタイピング体験に集中する。
- 常時アニメーションを前提にしない。既存LVGLで静止画や表情差し替えとして成立する見込みだが、実機での負荷は未測定。

## 次の検証で見る点

1. 実寸に合わせた描き起こしで、最長単語・ミス修正・操作案内が読めるか。
2. 小さい顔でもスタックチャンだと認識できるか。筐体の細部より目・口・3ボタンを優先する。
3. 無反応と単語確定時の反応を比べ、邪魔に感じないか。
4. 結果画面にオンライン送信中・成功・失敗の表示を加えても、スコアが読めるか。
